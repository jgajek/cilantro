# Recovery architecture

This is the technical recovery reference. Analysts can start with [workflows](analyst-workflows.md), [output interpretation](reading-the-output.md) and [support](compatibility.md). Detailed experiments below are evidence for specific transformations, not a separate current support matrix.

CILantro reads PE metadata and CIL with dnlib and uses a bounded interpreter for supported recovery paths. It does not load the sample into the host CLR to invoke its methods. Modeled framework operations act on interpreter-owned values, heaps, resources, and streams.

## Pipeline

Integer helper recovery can expose a proven constant while retaining the original call when its declaring type has initialization work. This preserves the exact initialization trigger and any effects or exceptions; it does not declare the initializer inert. Literal arguments separated from helper calls by no-ops can be recovered only when no branch or exception boundary enters the intervening sequence. The same argument check applies to closed numeric-table reads.

Numeric-table recovery accepts private `int[]` tables stored in `object` fields, with either a direct element read or an explicit array cast. Object-backed stores must receive fresh Int32 arrays, and alias tracking follows casts until the array is consumed; an escaping reference or a later writer prevents recovery. A late numeric-table pass retries getters exposed by loader and control-flow cleanup. Recognition alone does not authorize replacement: initialization dependencies, ambient inputs and independently interpreted values must still pass the existing checks.

When late recovery finds literal table calls, it also revisits module initialization. Reconstructed code may now expose a file-integrity rejection that early bootstrap could not observe. The existing bootstrap policy can then retry the assembly as memory-loaded, with that environment change disclosed in the report. The initialized machine is discarded: constant recovery still uses two fresh machines with no host assumptions. This retry neither removes the integrity check nor relaxes construction-dependency checks.

Numeric-table dependency analysis can follow a uniquely assigned readonly static delegate to its local static target. It checks the binding path, delegate signature, writes and address exposure, and ties the invocation to its receiver within the same basic block. Unconditional initializer jumps are supported; conditional bindings and cycles refuse. This proof does not replace delegate calls or bypass initialization: target dependencies still need checking, interpreted values must agree, and required initializer effects remain in the output.

If normal interpretation stops in initialization, a narrow fallback can evaluate a self-contained table constructor separately. Its reachable code must construct fresh objects without static inputs, external operations, addresses or unknown dispatch. The preceding initializer work is also checked: scalar writes and supported read-only ambient queries are allowed, but reference publication, unknown external calls and broader effects refuse. Initializers triggered by local helpers are included in that check. Two fresh bounded interpretations must agree, and every replacement retains the original initialization trigger, including its effects and failures. This does not authorize skipping a general Reactor loader or assuming a FIPS/debugger setting.

Local class references read by table construction also undergo a bounded consumer check. It follows borrowed references through control-flow joins, locals, arguments, instance-field aliases and local returns. Writes through a borrowed reference, unknown call escapes, exposed returns and addresses are refused. This guards both ordinary and independent-construction recovery against treating a readonly reference as an immutable object. The check covers direct CIL consumers after publication; it does not prove construction independence, exclude hidden aliases created before publication, or authorize reflection or loader bypasses.

Late recovery has a separate construction proof for loop-built lookup arrays and trees. After a leading sequence of argument-free, void initializer calls, the construction region must obtain every value from constants, fresh objects, or its own definitely assigned fields. Local construction helpers cannot read or publish static state. Every field produced by the region must be assigned on every return, and the consumer check follows all publications together, including aliases created during construction. Unknown calls, input-dependent construction, writes through published arrays, and exposed metadata tokens refuse the proof. This is a direct-CIL ownership proof, not a general reflection analysis. The leading calls still execute during bounded interpretation, and replacements retain required initialization triggers and effects.

The construction proof is kept out of early numeric recovery: preserving initialization effects before loader cleanup can obstruct later unflattening. Final numeric recovery runs again after reachability and unwritten-guard cleanup, when previously conditional construction paths can become recognizable. If it recovers constants, a final control-flow pass consumes them; otherwise that extra control-flow scan is skipped. This ordering exposes late constants without removing retained integrity checks or assuming host-dependent values.

Reproducible assemblies captured before a loader stops remain available for extraction. The pass reports partial recovery when a candidate fails, captured bytes fail validation, or the candidate limit is reached. A loader that exhausts its initial step budget is eligible for the larger bounded retry even if it already captured an assembly. These diagnostics do not prevent ordinary verified output, but `--fail-on-partial` continues to enforce incomplete-pass failures.

The loader search continues after the first recovered assembly because independent candidates can load different payloads. Recovered images are deduplicated by SHA-256. At most 24 candidate roots, including the entry point, are interpreted; additional candidates are reported as unexamined. This remains a bounded search rather than a claim of exhaustive extraction.

Payload extraction checks candidate loader paths before concluding that resource accounting leaves nothing to extract. An assembly can construct payload bytes from initialized fields or code without embedding a resource. If a discovered loader cannot be interpreted successfully, an empty resource table does not turn that failure into a successful extraction check.

1. Inspect the input, identify supported protection, and preserve its identity and original bytes.
2. Recover supported encrypted method bodies and strings, then expose constants and call targets needed by later passes.
3. Simplify control flow, interpret supported VM programs, restore resources, and extract embedded assemblies.
4. Reconstruct supported VM bodies, revisit newly exposed cleanup opportunities, and remove attributable protector infrastructure where dependency checks permit it.
5. Rename eligible symbols, verify the transformed assembly, and emit files and reports under the configured success policy.
6. When requested, traverse extracted assemblies with shared hash deduplication and depth/count/byte limits. Supported native wrappers automatically continue through their managed stage.

This is a conceptual sequence. The authoritative pass ordering and dependencies are in `CilantroPipeline.CreateDefaultPasses`; several recovery/cleanup passes run again after other transformations expose new information.

## Evidence and assumptions

Late embedded-dependency recovery queries structurally identified, resource-backed assembly resolvers with declared assembly-reference names. It also discovers candidate names in the resolver's static hashtables when two cold, distinct missing-name requests finish without loading an assembly and yield identical key sets. This can expose bundled dependencies absent from the reference metadata; the snapshots are candidate discovery, not an all-states completeness proof. Two fresh positive responses must return identical validated managed bytes with matching dependency names and one exact unchanged resource source. Captures join the ordinary payload artifacts and reports; the stage does not replace the resolver or alter loading behavior. Candidate/request counts and a shared 768-million-step budget bound the work, subject to declared budget overrides. Other table states, unsupported resolver shapes and declined responses remain outside this coverage.

With ordinary CLI reconstruction enabled and non-strict interpretation, a bounded reconstruction pass can expose a supported Reflection.Emit stream decoder as ordinary CIL. It captures the generated body without supplying stream contents, rejects state-dependent construction, and retains the original factory signature, domain writes, and reflected-call exception wrapping. It runs after final constant and control-flow cleanup. The replacement carries `ReconstructedEmittedMethodAttribute` and report evidence: generated assembly/type/method identities are not preserved, and this is analyst reconstruction rather than established equivalence. Strict runs retain the factory. Unsupported generated declarations and exception regions are declined.

Recovery records observations, source locations, changes, host facts, blockers, and declared outcomes. Default interpretation can use a plausible host profile and continue past some unsupported operations. Strict interpretation refuses these implicit assumptions. Neither mode can recover bytes that are absent from the file or prove caller-supplied facts true.

Instruction and body transformations use transactions: capture the original, edit, verify, then commit. Failure or early exit restores uncommitted bodies and discards their pending change records. Changes to metadata, fields, and resources require their own ownership and rollback discipline.

Field type restoration requires every writer to agree on a concrete reference type. It recognizes array allocations, typed locals and copies from typed fields, propagating proved types through field-copy chains before changing metadata. Assembly identity participates in type comparison: matching names from different assemblies do not count as agreement. Alternate entries into stores, exposed field addresses, conflicting writers and ambiguous object locals prevent these promotions. The pass changes field signatures without adding casts or changing instruction order.

## Control-flow simplification

After final control-flow recovery, instruction compaction removes no-ops and unconditional branches whose destinations are the next retained instruction. It redirects branch and switch targets without changing switch entries, retains debug sequence points, and preserves exception-region boundaries and their predecessors. Conditional branches, `leave` instructions, self-loops and terminal padding are retained. Each method is transactional and refuses a change that adds stack-analysis diagnostics.

Constant propagation tracks integer values carried on the evaluation stack across ordinary block boundaries when stack-depth analysis is valid. Stack slots and locals must agree across every incoming path; conflicting loop edges discard the affected facts. Calls and field reads consume their actual operands and produce unknown results, preserving constants below them without removing their effects or possible exceptions. Exceptional entries and `leave` edges discard carried facts. This exposes dispatcher states previously hidden by intervening guard reads and branches.

Dispatcher recovery also consumes the value proven at an individual local store. Different stores can supply different known states to a shared dispatcher even though the merged local value is unknown. The rewrite keeps the original computation and store, bypasses only the supported pure dispatcher path, and preserves its final local value. Calls before the store still run; calls inside the path being bypassed, unknown store values, address-taken locals, and changes of exception region prevent that specialization.

After dispatcher removal, unread Int32 state stores can become discards while their producers still execute. Conditional branches and switches can then collapse when every outcome reaches the same instruction after the same number of discards through no-ops and unconditional branches. Operand evaluation, field reads, calls, and their exceptions remain. Cycles, different effects or discard counts, exception-region changes, and `leave` paths prevent this collapse; it does not assume that a protector field has a particular value.

Within each basic block, recovery also tracks integer literal producers underneath intervening stack operations. A literal consumed only by a later pop can become padding along with that pop, even when calls or field reads intervene. Those effects remain in order. Branch and exception entries reset this tracking, and duplicated values lose their producer identity so that a live copy cannot be removed.

Dispatcher path recovery also handles branches that carry a constant on the evaluation stack into a shared state-variable store. It traces only supported, non-throwing integer operations in the same exception region, then preserves the final local write before redirecting the branch. Calls in the traced path, unknown state, and address-taken locals prevent this rewrite. A zero-argument static call whose result is discarded may remain at the source; the recovered local write stays after that call, preserving the old value if the call throws. A late recheck consumes paths exposed by the intervening dispatcher, helper, and generated-body cleanup.

Pure dispatcher paths may include integer duplication/discards, signed or unsigned division and remainder, and Boolean branches whose condition is known on that path. Zero divisors and signed overflow prevent bypass, as do calls, unknown operands, cycles, and exception-region changes. State updates made along the selected path are retained in the source local before the direct branch.

Tracing follows additional Int32/UInt32 temporary locals when their values are established along the selected path. It retains every final local write before redirecting the branch, including temporary values used by the destination rather than by the dispatcher itself. Unknown incoming temporary values and address-taken locals prevent bypass. This applies to literal entry states, shared stack-carried stores, and states proven at computed stores.

Known-state tracing also resolves signed and unsigned comparison branches, including methods with no switch. Constant propagation carries comparison results, non-throwing division/remainder results, and explicit 8/16/32-bit integer conversions into local stores. Narrowing uses the CIL signedness; native-sized and checked conversions are excluded from this extension. A potentially throwing arithmetic operation never supplies a guessed constant.

After shape-based recovery, runtime cleanup, and final numeric-table recovery, a separate effect-preserving dispatcher pass specializes supported paths containing direct/virtual calls, object construction, and field reads. It copies the selected instruction prefix to the incoming edge in execution order and replaces only a proven branch decision. Call and field results remain unknown; their evaluation, initialization triggers, and exceptions remain. Local loads proven on that edge can become literals, but writes visible to the destination or an exception handler are retained at their original relative positions. Handler checks include later filtered catches, not just the source's enclosing handlers. Dead copied stores become discards so their producers still execute.

The late tracer can follow successive proven branch decisions, retaining a snapshot of the last proven target when a later condition or instruction is unsupported. It folds known non-throwing integer arithmetic in copied paths while preserving operand evaluation and intervening effects. Literal/discard pairs introduced by folding are removed before insertion; potentially throwing arithmetic remains. Unknown state, cycles, and exception-region changes stop further traversal.

Entry state is taken from converged local-constant analysis at the source branch. A defining store may precede intervening calls or reads, and a value can also arrive through earlier blocks, joins or loops when every incoming path agrees. Later unknown writes invalidate it; address-taken locals remain excluded and exceptional entries and `leave` edges discard normal-flow facts. The pass prioritizes values defined in the source block before inherited facts because candidate order affects which dispatcher paths remain recognizable within the rewrite budget.

This late placement is essential: earlier cloning can obscure the patterns required by existing dispatcher recognizers. Tracing is bounded to 16 blocks and 64 input instructions, with at most 64 rewrite rounds per method. Address-exposed state and unsupported prefixes are excluded from tracing. Copying paths can increase assembly size even when the decompiled control flow becomes simpler; it does not prove that every surviving switch is protector code.

After runtime cleanup, another recheck finds tiny helpers that return an unwritten reference field or compare it with null. Under the existing non-strict unwritten-field assumption, it exposes the result to branch recovery while retaining the original helper call and field read, including their initialization effects and exceptions. Direct writes, field-address exposure, unsupported helper bodies, or an incomplete unwritten-field proof prevent recovery. Strict mode disables this assumption. Structural verification checks the result before changes are committed; it does not establish general behavioral equivalence.

Control-flow simplification can propagate proven integer-local constants inside methods with exception handlers. Catch, filter, finally, and fault entries start with unknown local values. A `leave` also discards incoming facts because intervening finally handlers can change them. Normal branches still require agreement at every join, and address-taken locals are excluded. This enables additional unflattening without assuming that exception paths preserve the normal-path state; it does not fully model exception-driven dispatch.

## Removing protector code

Cleanup needs both attribution and dependency analysis. An unused application method is not automatically protector debris. Initializers may decrypt data while also setting state used later; removing the entire initializer can break that state even when its decryption work is obsolete.

Loader cleanup therefore distinguishes the loader body from type-initialization effects. Integrity specialization preserves argument evaluation and shared initialization while replacing only a proven signature-check verdict. Reflection, numeric token lookups, indirect dispatch, and external contracts can require keeping declarations that direct-call analysis would otherwise remove.

## Verification boundaries

Structural verification, bounded reconstruction comparisons, successful decompilation, and benign runtime-oracle testing answer different questions. Emission gates prevent selected incomplete stages from producing a cleaned assembly; optional stages can remain partial while useful output is written. `--fail-on-partial` strengthens that policy but is not an equivalence proof.

Reconstruction comparisons include modeled current-domain data alongside returns, arguments, static fields, network settings, and native memory. The same bounded object graph captures aliases between domain values and other roots; the separate non-VM comparison also includes domain data and detects sharing with VM objects. `AppDomain.SetData` remains an effect that cleanup must preserve, but no longer makes a trial inconclusive solely because it stores domain data. Unknown or over-budget values still prevent agreement.

Assembly and resource resolver subscriptions are inspected rather than stopping the comparison immediately. Their ordered delegates, method identities, binding forms, target objects, and aliases participate in the domain snapshot. A captured difference produces disagreement; matching captured state remains inconclusive because callback behavior has not been compared. This applies to registrations made during module initialization as well as the measured call. Other unmodeled registrations still stop the comparison. A matching final snapshot does not prove callback behavior, generated runtime identities, or equivalence for all inputs.

The interpreter models `Hashtable.Keys` as a live view, retaining the original key objects and invalidating enumerator advancement/reset after writes. Enumeration storage respects the interpreter's allocation limits. Key order follows the interpreter's deterministic table model; it does not reproduce a particular CLR's bucket order, which the [Hashtable contract leaves unspecified](https://learn.microsoft.com/en-us/dotnet/api/system.collections.hashtable.keys?view=net-10.0). Order-sensitive callbacks still require additional validation. Unsupported collection operations remain explicit refusals.

Reference-type `box` instructions preserve identity, including null and arrays of value types; generic boxing uses the instantiated type. Reference-target [`unbox.any`](https://learn.microsoft.com/en-us/dotnet/api/system.reflection.emit.opcodes.unbox_any?view=net-10.0) performs a cast without extracting boxed contents, preserving aliases; incompatible casts are refused. Array-length queries refuse non-array objects instead of treating them as empty arrays. These distinctions matter when reconstructed VM methods pass tables and buffers through object-typed calls.

See [code organization](code-organization.md) for implementation entry points and [corpus validation](corpus.md) for reproducible checks.


For resource-backed dependency resolvers, the recovery stage can also validate a bundle index constructor independently of a successful dependency request. It checks that construction starts from a fresh table on every relevant path, admits only a bounded set of stream/string/table operations and fresh record constructors, and requires two fixed-input evaluations to agree. The saved snapshot identifies its source resource by name and hash. This is a construction proof only: decoder replacement additionally needs caller-source ownership, consumer immutability and initialization/locking preservation.


A separate dependency-index source check follows every direct index-constructor call. It requires the module's own assembly, an exact resource name (including supported closed delegate decoders), and a fresh unconsumed stream on every reaching path. Stream aliases, overwrites, prior consumption and unestablished exception paths refuse this check. A source-closed index still needs consumer-mutation and decoder-effect proofs before its encrypted loading path can be replaced.


Dependency-index consumer analysis tracks reference aliases through lookup, enumeration, typed out parameters and exception handlers. It refuses mutation or escape of the private table and recovered integer record fields while allowing the resolver's assembly/path cache updates. Construction separately checks the values at each table insertion, so agreement of final snapshots cannot hide an offset changed after publication. These facts still require decoder-input provenance and effect preservation before a replacement can be emitted.


For a closed dependency index, decoder-input analysis tracks exact resource positions through seeks, length decoding and complete BinaryReader buffer reads. Buffer aliases keep their provenance; mutations, escapes, partial reads, uncertain paths or reused input streams refuse it. Each direct decoder call must receive an established slice through a fresh inline MemoryStream. The saved bytes are inputs to a later effect-preserving decoder replacement, not authorization to omit decoder side effects or shared initialization.

The dependency decoder completion stage rechecks those source and ownership facts, then evaluates the fixed input twice with a restricted interpreter. It refuses ambient effects, writes to caller-owned bytes, open static inputs, unsupported object lifetimes and reentrant shared initialization. Closed lookup-table initializers are retained explicitly. Replacement is limited to callers that immediately consume the returned MemoryStream through the framework ToArray method, so other observable stream behavior is not assumed away.

An accepted decoder becomes a short helper that returns a fresh stream over the recovered bytes, stored as ordinary initialized data rather than encrypted code or a large string literal. The resolver's request selection, table construction, cache, locks and assembly loading remain in place. Structural verification accounts for the exact added declarations before committing; the ordinary runtime cleanup gates then remove only attributed helpers with no surviving references. The current replacement bound is 1 MiB. This does not by itself authorize deletion of the original bundle or other resources still read by application code.

Closed bundle-index construction can then become an explicit table initializer. Two construction traces must agree on constructor arguments, publication order, values and record aliases. The replacement calls the original pure record constructors, retains any integer assignments made before publication, allocates fresh decoded-name strings and preserves the source stream's final position. It is interpreted again and compared before committing. Interned literal inputs, repeated table publication and incompatible constructor argument widths refuse materialization. Selection, caching and synchronization remain in the resolver; removing its remaining stream reads requires a separate lifetime and use analysis.

Once both the decoder and index have been replaced, input-use analysis can retire the encrypted stream reads. It requires an input-independent recovered-data helper, fixed read/seek results on every reaching path, and no buffer-content observation or reference escape. Runtime-type tests and incompatible casts refuse this step; taking a local's address anywhere also prevents treating a subsequently assigned protected reference as private. Fixed reads become their established results, the resource open becomes a fresh empty stream, and the index's now-unobserved position update disappears. Observable allocation identities and lengths, request selection, caches and loading behavior remain. Exact retired source hashes feed resource cleanup, whose independent remaining-access and application-resource checks still apply.

Resource-access classification distinguishes closed metadata expressions from potential readers. A scoped AssemblyName(string) immediately consumed by FullName is only name parsing. An own-type assembly reference used solely by safe casts, stack copies and discards within a basic block cannot escape to a reader. These expressions remain in the output with their original exception behavior. Unknown reflection and dynamic assembly loading still block resource removal; classification alone does not authorize deleting application behavior.

After input retirement, a generated nonempty payload helper whose callers only consume its stream through immediate MemoryStream.ToArray can return its initialized byte array directly. Exact helper shape and all direct uses are rechecked. This avoids the wrapper and a redundant payload-sized copy while preserving independent mutable arrays and shared initialization. Empty payloads are excluded to preserve possible shared-empty-array identity; escaped streams and alternate entries are refused.

Unused dependency-input objects can also be retired after the read proof succeeds. A fresh MemoryStream passed directly to an input-independent helper is unobserved. BinaryReader and byte-buffer allocations qualify only when their references neither escape nor participate in identity/null comparisons; ambiguous aliases retain them. Every observed buffer length becomes its proven native-sized value, and exact framework casts established by the tracked runtime types are redundant. This removes the old encrypted buffer and reader without changing payload bytes, request selection or cache behavior. The fresh source-stream identity is still retained where the resolver observes it.

Late control-flow cleanup tracks discarded stack copies and literal conversion chains within basic blocks. It removes an unused duplicate while retaining its original producer, preserves checked conversions and effectful evaluations, and only removes unread reference stores when their value is proved null. Block entries and address-taken locals remain conservative. This also clears scaffolding exposed by dependency-input retirement. Shared immutable histories avoid quadratic work on long conversion chains.

Retired encrypted dependency bundles have a narrower resource-removal rule under the accepted contract allowing deliberate protector-metadata removal. After input retirement and direct-array replacement commit, a run-local proof captures the exact source hash, resolver/index/helper bodies and signatures, and the replacement managed payload's initialized-data hash and layout. Cleanup revalidates these before deleting the bundle. A small set of framework assembly-loading, type/method-enumeration and delegate-invocation calls may remain unchanged; this exception applies only to the certified bundle, not other attributed resources. Explicit resource readers, unknown native access, other reflection, literal references, application-resource roles and stale proofs still prevent deletion. Reflection that deliberately inspects the removed protector metadata is outside the preservation contract; application logic and replacement payload bytes remain in place.

The same limited metadata-observation rule applies to exact resources whose validated numeric, integrity, method-patch or NecroBit owners have been physically removed. Each ownership provider retains its own prerequisites, including completed method recovery where required. A successfully decoded string or proxy resource alone does not establish owner retirement and cannot use this exception. Duplicate resource names, changed bytes and surviving readers still refuse removal.

Successful string rewrites also record their exact resolver-alias family against the decoded input hash. Successful proxy rewrites record their resolver candidates and proxy types. Cleanup admits these inputs only after every recorded method/type is physically absent; repeated observations of the same source are combined so one removed reader cannot hide another surviving reader. Merely decoding the input is insufficient. These ownership facts still pass the common exact-byte, unique-name, application-role and remaining-access checks, including conservative ResourceManager/reflection checks.

Generated ResourceManager getters can now establish a bounded application-resource scope. The proof requires the framework constructor, a literal base name, an own-type assembly, and a private cache with one writer and no address exposure. Local declarations alone do not invalidate it; unsupported instructions and alternate entries do. Calls through that cache/getter are traced within one basic block. Every manifest name ending in `.resources` is reserved, including culture variants and case variants. No application resource-loading IL is rewritten.

For positively retired protector inputs only, reflection on a receiver traced from framework `Assembly.Load(byte[])` through `GetType(string)`, `GetMethod(string)` and `Invoke(object, object[])` can remain under the accepted metadata-removal contract. Overwritten/addressed locals, own-assembly handles, unknown receivers, foreign framework lookalikes and cross-block uncertainty still refuse that classification. This is not a general exemption for reflection or resource access.

Restored encrypted resource bundles also record their original reader methods. Their retirement requires all those methods to be physically absent and every reattached application stream to retain its exact recovered name and hash. Empty restoration, changed/missing/duplicate application streams, surviving readers, source changes and the common remaining-access checks prevent removal. The unencrypted application resources stay in the assembly; cleanup removes only the redundant encrypted input.

Self-integrity helper attribution can combine independent successful string and proxy recovery on the same runtime owner, without relying on the namespace looking generated. It nominates only the recognized self-file checker for the normal dead-method/reference checks. It does not mark the containing type or unrelated unused siblings for deletion; live calls and retained references still prevent removal.

Unused Reactor singleton guards are recognized as an object-typed field with exactly two reads: a generated-name own-type getter and its generated-name null-test helper. Writes, addresses, extra readers, explicit member names and incompatible declarations refuse recognition. Only methods that also pass the existing dead-method/reference checks are removed. Their backing field disappears only when both methods are physically absent; surrounding application types, methods and initialization stay intact.

Late integer finalization runs again after dependency initialization cleanup. Calls that were previously retained solely for type-initialization effects can then become explicit constants if their initializers have been safely retired. The bounded pure-integer proof is unchanged, and observable initialization still prevents call removal. Declaration cleanup follows before shared-initializer retirement, allowing an otherwise unused compression-helper graph to disappear once its last integer-helper consumers are gone.

Array-parameter typing also recognizes array API arguments, constructor arguments, typed local spills and returns. These uses identify where erased metadata needs repair; every closed caller must independently supply the same concrete array type before casts are inserted. Unknown or conflicting callers still prevent the rewrite, and public signatures remain unchanged.

The same closed-caller analysis also restores string and concrete class parameter stack types. Every caller must establish exactly the same reference type; API expectations alone are insufficient. This leaves method signatures intact and inserts explicit casts at parameter reads, improving verifiability of Reactor-erased object parameters while refusing unknown or conflicting callers.

Reference-field repair preserves the original object field signature. It requires all closed writers to agree on a concrete reference type, tracing stack values within one basic block through object construction, duplication and intervening setter calls. It then inserts explicit casts at untyped reads. Addressed or reflectively exposed storage, conflicting writers and control-flow entries inside the proof prevent repair. Parameter provenance also retains reference types established by `isinst` and concrete reference-array element reads. Existing casts separated by NOP padding are reused rather than duplicated.

Reference-stack repair preserves method signatures and requires concrete caller evidence. For private static non-accessor helpers, an exact framework PropertyDescriptor.ComponentType getter can be treated as metadata when there are no observed local readers, method-pointer uses, named reflection uses or local descriptor subclasses. This follows the recovered-application preservation scope; arbitrary external reflection over the publicly returned Type is outside that scope.
